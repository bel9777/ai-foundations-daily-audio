AI Foundations — Day 42: Tools and Function Calling

Why This Matters

When an AI needs an exact answer, current information, or a safe connection to another system, words alone are not enough. Tools let a model ask software for help: calculate a total, look up a record, search a document, or format a result. Today you will learn the simple loop behind that handoff and the checks that keep it reliable. Start with this question: when should an AI answer from its own language ability, and when should it ask a trusted tool instead?

The Mental Model

Think of a language model as a capable office assistant. It can read a request, explain a policy, and decide what information would help. But it is not a calculator, a calendar, a database, or a shipping system. A tool is one of those external capabilities made available through software. Function calling is the controlled way the model asks to use one. Instead of writing a loose sentence such as please look up this order, the model produces a structured request with a tool name and arguments. Arguments are the specific inputs the tool needs, such as an order number, a city, or a date. Your application checks the request, runs the approved tool, and returns the result to the model. Then the model turns that result into a useful response. That sequence is the tool loop: user question, tool request, application execution, tool result, final answer. The separation matters. The model decides what would help. Your software decides whether the action is allowed and how it happens. Good tools stay narrow. A calculate total tool calculates; a search documents tool searches; an order status tool finds an order. Narrow tools are easier to test, easier to validate, and less likely to be used for the wrong job. They also make permissions clear. The model should never quietly invent access just because a user asked. Tools extend the model’s reach, but the application owns the boundary around that reach. Before a result returns, the application can check authorization, limit the fields exposed, and record what happened. After a result returns, the model should use that result rather than restating an old assumption. This division turns a vague request into a repeatable process. It also gives people a place to improve the system: tool definitions, input checks, permissions, and the final response format. The model is one participant in the loop, not the unchecked owner of it.

A Real-World Example

Imagine an online store support assistant. A customer asks where an order is. A language model should not guess that it shipped. Instead, it recognizes that the answer depends on current order data and requests an order status tool with the order number. Before running it, the application confirms that this is an approved tool, that the order number is present, and that the customer is allowed to see the result. The tool returns a current status, perhaps shipped with an expected delivery day. The application passes that result back to the model. Only then does the model write a friendly answer. This is better than a polished guess because the response is tied to current information. Retrieval can work alongside tools here. A document search may find the shipping policy, while the order status tool finds this customer’s actual shipment. One supplies policy context; the other supplies a precise lookup. If either result is missing, the assistant should say so rather than inventing an outcome. The assistant could also ask a clarifying question if no order number was provided. That is safer than searching broadly for a customer’s private records.

Pause and Practice

Pause the episode and write down three small tools you might want for a personal or work assistant. They could be calculate sum, search notes, and get date. For each one, name the inputs it needs and the result it returns. Then write five questions. Decide which can be answered directly and which need a tool. For every tool question, specify the exact tool name and arguments. Pause now and try it. Here are the answers to check yourself. A function call is a structured request for software to run a particular tool with particular inputs. Narrow tools are usually better than one giant tool because they are easier to test and validate. A basic safety check is to validate the requested tool and its arguments before execution, then reject invalid or unsafe requests. Also treat instructions found in untrusted documents as data, not permission to act. That prevents a retrieved document from redefining your system’s rules.

Recap and One Action

Three takeaways. First, tools give a language model access to approved lookups or actions it cannot perform reliably by conversation alone. Second, function calling uses a structured request, then a checked tool loop, rather than an improvised guess. Third, narrow tools and argument validation make the system easier to control. One action for today: choose one recurring question you answer with current information. Write a one-line tool design for it: tool name, required inputs, allowed result, and one safety check. Keep it small. That design will reveal whether a tool is truly needed and what your application must verify before it runs. Start there.
