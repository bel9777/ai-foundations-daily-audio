Alex: And to make it representative, it has to match the actual mix of inputs real users are going to throw at it.
Jordan: Right. Think of it like tasting soup before you serve it to guests. If you only dip your spoon into the top layer, you might think it tastes great, but you will miss the fact that the spices sank to the bottom and the rest is bland.
Alex: So you need a spoonful that reaches all the way to the bottom of the pot. What makes a test set reach the whole pot?
Jordan: Three key qualities: coverage, balance, and difficulty mix. Coverage means you include all the main kinds of requests you expect. Balance means you are not flooding the set with one easy category while ignoring the rest.
Alex: And difficulty mix means you do not just test the simple stuff, you give it medium and hard prompts too.
Jordan: Spot on. The biggest mistake people make is building these sets out of pure guesswork. You have to start from real use cases, which are the specific jobs your system exists to do.
Alex: Like, if I build a support bot for an online store, a use case might be answering questions about shipping.
Jordan: Right. From there, you break that use case into input categories. For that support bot, that might be simple factual questions, ambiguous requests, prompts that need a tool, questions grounded in source documents, multi-turn chats, or nasty edge cases.
Alex: If I only test "Where is my package?" and it gets a ninety-five percent, I might feel great, but I am actually just being overly optimistic.
Jordan: Exactly. You are testing one tiny category.
Alex: How do edge cases fit in? Because by definition, edge cases do not happen all the time.
Jordan: They do not happen often, but when they do, they can wreck your user experience or cost you real money. A good set has typical cases, near-boundary cases that are almost simple but not quite, and failure-prone cases where the model has messed up before.
Alex: Is there a good rule of thumb for what counts as an edge case worth testing?
Jordan: Here is the rule: if a failure would be annoying, risky, or expensive in production, it belongs in the eval set, even if it is rare.
Alex: Okay, so it is not just a random pile of prompts. How do you structure each test example?
Jordan: Every single example needs three things: the input prompt, the expected good behavior, and the reason that example matters. Behavior means something visible, like picking the right tool, citing a source correctly, or asking a clarifying question.
Alex: That way, when you update your model later, you know exactly why a test failed. But how do you know if you missed something big?
Jordan: You actively hunt for blind spots. You ask yourself: which user types are missing? Which writing styles? Are we testing tool failures or hard memory situations? Finding one blind spot is usually worth more than adding fifty duplicate easy cases.
Alex: Walk me through a full example. Say we are building that store assistant.
Jordan: If your test set only has "Where is my order?", the model looks brilliant. But a representative set forces it to handle real messiness. Like a customer giving an incomplete order number, or a question that requires calling a shipping tool.

Jordan: Exactly. Or follow-up questions that depend on conversation memory from three turns ago, or edge cases like canceled orders or international shipping rules.
