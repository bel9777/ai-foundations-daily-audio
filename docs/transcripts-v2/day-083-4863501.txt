Alex: The moment an AI stops just talking to you and starts actually touching your files, your calendar, or your inbox, everything changes. This is AI Foundations, day 83.
Jordan: Today we are talking about agents and tool use. Up to this point, we have spent a lot of time on models that take a prompt and hand back a response. That is a classic chatbot setup. One input, one output.
Alex: Right. I ask for a poem or an explanation of quantum physics, and it gives me text. But an agent goes further than that.
Jordan: Much further. An agent is a system that can take actions over time to achieve a specific goal. Instead of finishing after one sentence, an agent runs in a continuous loop: it observes what is going on, decides on the next step, uses an external tool if it needs to, inspects the result, and repeats until the job is done.
Alex: That word tool is key here. What actually counts as a tool for an AI?
Jordan: Any external software function the model can trigger. That could be a web search, a Python code interpreter, a calculator, a database query, or an API that reads your calendar. Language models are great at reasoning and language, but they are not equally good at everything. They struggle with raw arithmetic, and their training data is frozen in the past.
Alex: So the model acts like a manager or coordinator rather than doing all the manual labor itself.
Jordan: Exactly. If the task requires adding up six large numbers, the model should not guess the math. It writes the numbers into a calculator tool and gets the exact answer. If it needs to know your flight status, it pings an airline database. Tools give the model precision and real-time facts.
Alex: That brings us to how the agent actually operates day to day. You mentioned an agent loop.
Jordan: Think of it like a cook working through a dinner service. The cook has a recipe, which is the overall plan. The knives, pans, and stove are the tools. But the most important part of cooking is tasting the dish as you go. You do not just dump salt in and serve it. You add a pinch, taste it, see where the flavor is, and adjust your next move.
Alex: If you do not taste, you end up ruining the meal before you even realize you made a mistake.
Jordan: Exactly. In agent terms: you have a goal from the user, a rough plan of steps, an action taken using a tool, an observation of the output, and an update to your plan based on that observation. Without that observation step, the agent can get trapped in a ditch and keep digging.
Alex: How much should an agent plan ahead versus just jumping straight into taking actions?
Jordan: That is the big tension. If an agent tries to map out twenty steps in advance, the plan falls apart the second step two returns an unexpected error. But if it acts with zero plan, it flails around randomly. The sweet spot is usually making a short, rough plan, taking a single step, looking at the result, and revising.
Alex: That ties right back into yesterday’s lesson on retrieval and memory.
Jordan: It does. Before an agent acts, it uses retrieval to fetch context it needs right now, like relevant company policies. And it uses memory to track what it already tried so it does not repeat steps. But you keep that memory lean. If you dump every single log and thought into memory, you just drown the model in noise.
Alex: And when an agent is actually changing things in the world, mistakes get a lot more expensive.
Jordan: Much more expensive. That is why guardrails are non-negotiable. Guardrails are the explicit rules that bound what an agent can do. You might let an agent draft an email, but you put a hard block on it actually sending that email without a human hitting confirm. You limit file access strictly to approved folders. You block transactions over a certain dollar amount, and you log every single tool call.
Alex: That connects straight to what we covered on day 77 with safety and security. A tool is basically an open doorway into real systems.
Jordan: That is why workflow design matters so much. If you give an agent a vague assignment like manage my week, it will probably fail. But if you break that workflow into narrow, boring steps—read the calendar, find three free slots, draft an invite, ask the user to confirm—it works reliably. Plus, as we saw on day 79 with economics, every extra tool call costs compute, money, and time. Powerful agents that run wild are slow and pricey.
Alex: Walk me through a clean, real-world example of how this fits together.
Jordan: Take a travel assistant helping you reschedule a canceled flight. A basic chatbot just says, sorry to hear that, call your airline. An agent steps into the loop. First, it uses retrieval to pull your booking confirmation from your emails. Second, it checks the airline’s change policies using a browser tool. Third, it spots two alternate flights and drafts a change request. Fourth, it hits a guardrail: it pauses and asks you, should I book flight 402 for tomorrow morning? Fifth, once you click yes, it makes the change and writes the new confirmation into memory for the rest of your trip.
Alex: Planning, retrieval, tools, safety gates, and memory, all working in sequence.
Jordan: That is the whole architecture right there. Let us do our quick knowledge check. First question: what is the fundamental difference between a chatbot and an agent?
Alex: A chatbot just produces a single response to a prompt. An agent has a goal and takes a sequence of actions over time in an active loop to achieve it.
Jordan: Spot on. Next: why does an agent rely on tools instead of just generating the answers itself?
Alex: Because models are coordinators, not specialists. If you need live data, database records, or perfect arithmetic, external tools provide exactness where the model alone would hallucinate or guess.
Jordan: Exactly right. Last one: what is one guardrail you would put on an agent that handles messaging?
Alex: A human confirmation gate. Let the agent write the draft, but require a person to approve it before anything actually gets transmitted.
